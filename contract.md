# Evidence Model and Synthetic History — Contract

The record shapes below are the contract between the five issues of this
milestone. Everything is plain JSON under `fixtures/`, generated by
`generate.py` from a fixed seed, and validated by `check.py`.

## Record shapes

### Work item

| Field | Type | Notes |
|---|---|---|
| `item_id` | string | Unique synthetic id, `SYN-nnn` |
| `sprint` | int | 1-8 for completed sprints, 9 for the held-out backlog |
| `summary` | string | Invented one-line summary |
| `description` | string | 2-4 sentences |
| `acceptance_criteria` | [string] | 2-4 bullets |

```json
{
  "item_id": "SYN-101",
  "sprint": 1,
  "summary": "Migrate billing export jobs off the legacy scheduler",
  "description": "The existing jobs run on the legacy scheduler and are removed only after the replacement runs cleanly for a week. The new pipeline reads the same source tables and produces byte-compatible output files.",
  "acceptance_criteria": [
    "Replacement job produces identical output for a seeded week of history",
    "Old jobs are disabled only after the new job passes monitoring checks"
  ]
}
```

### Estimate

| Field | Type | Notes |
|---|---|---|
| `item_id` | string | Joins to the work item |
| `points` | int | One of 1, 2, 3, 5, 8, 13 |
| `confidence` | string | `low`, `medium`, or `high` |
| `factors` | [{`tag`, `reason`}] | Factor tags, each with a one-line reason |
| `notes` | string | Free text |
| `analogues` | [string] | Optional: ids of comparable earlier items |

```json
{
  "item_id": "SYN-101",
  "points": 2,
  "confidence": "medium",
  "factors": [
    {"tag": "migration", "reason": "historical migrations have exceeded base estimates"},
    {"tag": "operational-risk", "reason": "mistakes in this path are expensive"}
  ],
  "notes": "similar migration work has historically exceeded base estimates",
  "analogues": ["SYN-104", "SYN-107"]
}
```

### Outcome

| Field | Type | Notes |
|---|---|---|
| `item_id` | string | Joins to the work item |
| `actual_points` | int | Completed re-sizing in the same vocabulary (1, 2, 3, 5, 8, 13) |
| `engineering_days` | float | Engineering effort; the signal calibration learns from |
| `elapsed_days` | float | Calendar days; captured but excluded from learning |
| `override` | {`reason`, `corrected_estimate`} | Optional: a human rejected the estimate at the sanity check |
| `surprises` | [{`kind`, `detail`}] | Optional; `kind` is `new-dependency` or `scope-change` |

```json
{
  "item_id": "SYN-101",
  "actual_points": 5,
  "engineering_days": 2.3,
  "elapsed_days": 4.1,
  "override": {
    "reason": "underestimated the amount of cleanup the cutover required",
    "corrected_estimate": 5
  },
  "surprises": [
    {"kind": "scope-change", "detail": "backward-compatibility shim added mid-sprint"}
  ]
}
```

### Evidence

`item_id` plus the full work item, estimate, and outcome records, joined by id.
The embedded records are byte-for-byte the same objects as the standalone
files; `check.py` verifies the join.

```json
{
  "item_id": "SYN-101",
  "work_item": { "...": "..." },
  "estimate": { "...": "..." },
  "outcome": { "...": "..." }
}
```

## Factor vocabulary

A fixed set of nine factors, no subcategories, tags may overlap:

```text
migration, familiar-application, external-dependency, novelty, ambiguity,
unfamiliar-subsystem, cross-team, testing-burden, operational-risk
```

Three factors are *planted* — their ground-truth effect on effort is known and
is what the calibration step must recover. The other six are *neutral*: they
carry no planted multiplier. An item carries at most one planted factor, so
the planted rules never conflict; neutral tags may appear on any item.

## Planted generating rules

Actuals are generated as `estimate x (multiplier + noise)`, then snapped to the
nearest point in the vocabulary, because actuals are recorded in the same
units as estimates. The noise is bounded per factor:

| Factor | Multiplier | Noise bound |
|---|---|---|
| `migration` | 2.0 | ±0.1 |
| `familiar-application` | 0.7 | ±0.1 |
| `external-dependency` | 1.3 | ±0.6 (wide: high variance) |
| everything else | 1.0 | ±0.2 |

Noise values come from an evenly spaced grid across each factor's bound, and
the estimate sequences per factor are fixed, so the per-factor median of the
*recorded* `actual_points / points` recovers the planted multiplier by
construction instead of depending on the random stream:

| Factor | Completed items | Recorded ratio spread | Median actual/estimate |
|---|---|---|---|
| `migration` | 7 | 1.5-2.5 | 2.0 |
| `familiar-application` | 6 | 0.6-0.667 | 0.667 |
| `external-dependency` | 6 | 0.667-1.625 | 1.3 |

Because actuals snap to the vocabulary, an individual recorded ratio deviates
from the multiplier by more than the noise bound (e.g. a 2-point migration
records 3 or 5 points). The recoverable signal is the per-factor median, which
is what the acceptance criteria measure and what calibration must learn.

Neutral items use the same grid. With the ±0.2 bound only the two most-negative
slots snap below the estimate, so the neutral recorded ratios are mostly 1.0
with two exceptions at 0.625 and 0.667.

`engineering_days` is `actual_points x 0.5` with ±20% variation;
`elapsed_days` is engineering days plus 0-5 waiting days. Both are excluded
from calibration arithmetic, per the vision's effort-vs-elapsed distinction.

## Dataset

One synthetic team, 8 completed sprints of 5 items each (40 completed items,
ids `SYN-101`-`SYN-140`), plus a held-out Sprint 9 backlog of 12 items.

| File | Contents |
|---|---|
| `fixtures/work-items.json` | 40 completed work items |
| `fixtures/estimates.json` | 40 estimates |
| `fixtures/outcomes.json` | 40 outcomes (5 with overrides) |
| `fixtures/evidence.json` | 40 joined evidence records |
| `fixtures/held-out/backlog.json` | Sprint 9: 12 items and 12 estimates, no actuals |
| `fixtures/held-out/held-out-actuals.json` | Sprint 9: 12 outcomes. The only file that contains these actuals; only the evaluation step reads it |

Held-out counts per planted factor are 3 each (migration, familiar-application,
external-dependency) plus 3 neutral items.

Overrides: exactly 5 completed outcomes carry an override. `corrected_estimate`
is the actual points — the modeled human correction landed on what the work
really was. The PoC records the override; it does not run a live review.

All summaries, descriptions, notes, reasons, and ids are invented; there are
no real names, issue keys, or credentials anywhere in the fixtures.

## Calibration step

`calibrate.py` turns the committed evidence records into the bias report and
the guidance artifact with deterministic arithmetic only — the step contains
no model call and no network access. The report is `bias-report.json`, the
artifact is `guidance.txt` (the estimator's guided condition consumes it),
and both are updated in place by each run.

| File | Contents |
|---|---|
| `bias-report.json` | Current bias report: overall, per-sprint, per-factor, overrides, effort, elapsed |
| `guidance.txt` | Current guidance artifact in the fixed shape below |
| `runs/<sha256>/` | One retained directory per generation, named after the sha256 of the evidence file it was calibrated from; holds that generation's report and artifact |

### Learned numbers

Every learned ratio uses engineering effort only: the per-item ratio is
`actual_points / points` (the completed re-sizing recorded in the outcome's
effort vocabulary) and the effort section uses `engineering_days`. Elapsed
statistics are reported in their own `elapsed` section of the report and
never enter a learned number — a blocked item with extra elapsed days and
unchanged effort leaves every learned ratio byte-identical.

### Bias report

| Section | Fields |
|---|---|
| `overall` | `estimated_points`, `actual_points` (sums over the body), `ratio` (actual / estimated), `spread` (min and max per-item ratio) |
| `per_sprint` | One row per sprint: `sprint`, `items`, `estimated_points`, `actual_points`, `ratio` of the totals |
| `per_factor` | One row per vocabulary factor: `factor`, `observations`, then either `median_ratio` and `spread` (min and max), or `learned: "insufficient evidence"` when observations < 4, with no ratio |
| `overrides` | `overridden`, `total`, `rate` (overridden / total), and `items` listing each overriding item's id, reason, and corrected estimate |
| `effort` | `engineering_days_total`, `engineering_days_mean_per_item`, `engineering_days_per_actual_point` |
| `elapsed` | `elapsed_days_total`, `elapsed_days_mean_per_item`, and waiting days (elapsed minus engineering): `waiting_days_total`, `waiting_days_mean_per_item`, `waiting_days_max_per_item` |

### Guidance artifact

Fixed shape: one overall line then one line per vocabulary factor, in
vocabulary order — the line count never grows with the evidence.

```text
overall: <ratio> (<records>)
<factor>: <median ratio> (<observations>)     # learned factors
<factor>: insufficient evidence               # fewer than 4 observations
```

Ratios are printed to three decimals. The artifact is regenerated in full
from all evidence on every run and contains no per-item content.

## Evaluation step

`evaluate.py` scores a recorded run directory against the held-out actuals
with pure arithmetic only — the step contains no model call and no network
access. It requires exactly one recorded call per condition and held-out item
(36), each matching the committed backlog item and context under one model
and endpoint, refuses an incomplete or inconsistent run, and writes two files:

| File | Contents |
|---|---|
| `evidence/verdict.md` | Prose verdict: one section per check with the measured numbers and an explicit pass/fail, plus the overall verdict |
| `evidence/results.json` | Machine-readable results with the same numbers |

Metrics: the total ratio is the sum of a condition's estimates over the sum
of the held-out actuals; per-factor totals use each planted factor's three
held-out items as fixed by the committed backlog estimates; sizes are the
character counts of `guidance.txt` (the artifact) and
`fixtures/evidence.json` (the raw history context).

| Check | Rule |
|---|---|
| V1 baseline sanity | unguided total ratio within [0.5, 2.0] |
| V2 learning transfers | guided total ratio closer to 1.0 than unguided by at least 0.05 |
| V3 compaction | guided and history total ratios within 0.05 while the artifact is at most one fifth of the history context |
| V4 bias recovery | for each planted factor, the guided factor ratio is closer to 1.0 than the unguided one |
| V5 guardrails | every estimate in the point vocabulary, no day fields in the learned numbers, calibration from the committed evidence only (the run directory stays byte-identical) |

Overall PoC success means all five checks pass. A failing check is a recorded
finding in the verdict, not an incomplete deliverable. The verdict is
computed from recorded calls — replaying the run directory reproduces it
exactly without the model — and the verdict files carry aggregate numbers
only, so the held-out containment of `check.py` still holds.

## Checks

```sh
python3 generate.py   # writes fixtures/ from the fixed seed (byte-identical on rerun)
python3 check.py      # validates the fixtures against the acceptance criteria
python3 check_calibration.py   # validates the calibration step against the acceptance criteria
python3 check_estimator.py     # validates the estimator step against the acceptance criteria
python3 check_evaluation.py    # validates the evaluation verdict against the acceptance criteria
```

`check.py` regenerates the fixtures twice into temp directories and compares
byte-for-byte (and against the committed copy), then reports the counts, join
integrity, per-factor medians, held-out containment, and vocabulary checks.
The check scripts use only the standard library and make no network calls.
